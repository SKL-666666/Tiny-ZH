# E2.2 — Tiny-ZH-64M-v1（失败的 SFT）

> 2026-11-15 | 已交付但质量差 | 得分 19/105（18.1%）

---

## 目标

把参数从 31.5M 提到 64.8M，上下文从 256 提到原生 1024，数据从问答式换成真实对话。

---

## 架构

```python
ModelConfig(
    vocab_size=6400, hidden_size=640, num_layers=13,
    num_heads=10, num_kv_heads=5, head_dim=64,
    intermediate_size=1792,        # FFN/hidden = 2.80
    max_position_embeddings=1024,
    rope_theta=500000.0,
)
# 64,816,000 参数
```

|---|---|
| 参数 | 64,816,000 |
| 层数 | 13 |
| hidden | 640 |
| FFN/hidden | 2.80 |
| 词表占比 | 6.3% |

## 数据（错误配比）

| 来源 | 占比 | 实际产出 | 问题 |
|---|---|---|---|
| **LCCC large** | **55%** | 3.74 亿字 | **平均 46 字/段，碎片** |
| FineWeb-Edu-v2 | 35% | 9.16 亿 token | 网页噪声 |
| ShareGPT | 15% | 1.29 亿 | 数据量小 |
| 中文维基 | 15% | 1.68 亿 | 相对最好 |
| COIG-CQIA | 5% | 0.4 亿 | 量小 |

**关键错误：`pretrain_t2t_mini`（最好的数据）完全没用。**

### 实测发现的数据坑

1. **LCCC 每行是 list 不是 dict** — 写 `o.get("dialog")` 会崩
2. **LCCC 字间空格占 38.1%** — `火锅 我 在 重庆` 必须挤成 `我在重庆`
3. **ShareGPT 字段是 `conversation[].human/assistant`** — 不是 `from/value`

## 实测结果：19/105（18.1%）

比 31.5M 的 7.6% 提升 2.4 倍，但**没有一条崩成英文**是最大进步。

### 失败类型分布

| 类型 | 次数 |
|---|---|
| 中文不足（崩英文） | **13** |
| 编号列表 | 3 |
| 太短 | 3 |
| 太长 | 2 |
| 复读问题 | 1 |

### 典型失败

| 问题 | 输出 |
|---|---|
| 你是谁？ | `[O] Lime，字典中的"A"是第一个元素...` |
| 推荐一本好书 | `[D. Sanogram, N. Hubliktabel] [A. Rachel...` 纯英文 |
| 怎么学习编程 | `1. 编写编译器 2. 编译代码 ... 15. 使用命令实现函数` 编号复读 |
| 今天天气怎么样 | `"你好，有什么想谈论的吗？"Mathematics回答道...Corplins Corvy` |

### SFT 数据的问题

用的是 **ShareGPT**，混了大量「列出1234」的任务指令，导致：
- 模型学会输出 `[1][2][3]` 格式
- 答案平均 1735 字，太长
- 简单问题只回 6 个字（复读提问）

---

## 结论

1. **LCCC 55% 是最大错误。** 46 字碎片占比过高，模型学不会长程连贯。
2. **FineWeb 35% 加剧问题。** 网页噪声稀释了中文质量。
3. **最好的数据（pretrain_t2t）没用。**
4. **SFT 用 ShareGPT 是错的。** 应该用 minimind 的 sft_t2t。
5. **9.42 亿 token（14.5×）比 minimind-3 的 2.5 亿（4×）多 3.8 倍，效果只有它的 26%。**

**归因：为凑 token 数牺牲了数据质量。**
